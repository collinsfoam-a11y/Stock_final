## 🔒 Template Waiting State Gate

**Stock Verify remains `READY_FOR_ERP_TEMPLATE_COMPARISON` until all blocking ERPNext inputs are present.** This gate exists specifically so a future agent or operator cannot accidentally advance the status without real ERPNext evidence -- do not edit the status in Section 1 to `READY_FOR_MANUAL_IMPORT_DRY_RUN` or beyond without first re-running `python scripts/check_erpnext_template_inputs.py` and confirming it reports `can_advance_to_manual_import_dry_run: true`. Machine-readable form: `docs/erpnext_templates/readiness_gate.json` (a static snapshot only -- the script, run live, is the actual source of truth).

**Blocking inputs** (all 10 must be present):

1. ERPNext version
2. Company name
3. Stock Entry template
4. Stock Reconciliation template
5. Serial/Batch Bundle status
6. Negative serial/batch stock rule
7. Serial import path
8. Batch import path
9. Stock Entry child-row import behavior
10. Stock Reconciliation child-row import behavior

**Warnings / conditional inputs** (do not block, but should still be resolved):

1. Frappe version
2. Serial No template, if the serial import path is used
3. Batch template, if the batch import path is used

**As of 2026-07-08: all 10 blocking inputs are still `"unknown"`/missing.** No templates have been received, and none of the version/behavior metadata has been fabricated to work around this gate.

1. Baseline is immutable once session starts.
2. Stock Verify variance = counted_qty - baseline_qty.
3. ERP drift = existing_sql_qty - baseline_qty.
4. Final gap = counted_qty - existing_sql_qty.
5. ERPNext adjustment_qty = counted_qty - existing_sql_qty.
6. ERPNext opening_qty = counted_qty.
7. SQL Server remains read-only.
8. MongoDB remains operational store.
9. Do not write directly to ERPNext.
10. Do not export unapproved count lines.
11. Do not export unknown unmapped items.

Mappings are deactivated, never deleted. Every mapping/flag create or update writes an `EXPORT_MAPPING_CHANGED` audit event with before/after. Admin-only CRUD API at `/api/erpnext-export-settings/*` (`require_admin`). Preview's `WAREHOUSE_MAPPING_MISSING`/`UOM_MAPPING_MISSING`/`BATCH_REQUIRED_MISSING`/`NEGATIVE_OPENING_QTY_NOT_ALLOWED` blockers now use these explicit sources instead of raw presence/inference checks; response rows additionally include `erpnext_warehouse`, `erpnext_uom`, and `uom_conversion_factor` when mapped.
- `company` is now required context for every preview: `POST /api/erpnext-exports/preview` accepts an optional `company` field that, if omitted, is safely auto-derived only when exactly one active company exists across warehouse mappings, otherwise the call fails with `COMPANY_REQUIRED` rather than guessing. Warehouse-mapping lookup and preview versioning/supersession are both scoped by (`session_id`, `mode`, `company`), so two different companies' previews for the same session/mode never collide or supersede each other.
- `POST /api/erpnext-exports/{export_id}/approve` (admin-only, `require_admin`): loads the preview by id, refuses to approve anything that isn't `READY_FOR_APPROVAL`, still has blockers, is `SUPERSEDED`/`CANCELLED`, or has no `company` recorded; re-validates that the session is still finalized, the approved count-line count is unchanged, and no new offline conflicts exist; never recalculates rows. On success it stamps `status=APPROVED`, `approved_by`, `approved_at`, and a SHA-256 `approval_hash` of the frozen payload, and writes an `EXPORT_PREVIEW_APPROVED` audit event. Approved previews are proven immutable: regenerating a preview for the same (session, mode, company) creates a new version and never mutates or supersedes the approved document.
- `GET /api/erpnext-exports/{export_id}/download/{stock-entry,stock-reconciliation,serials,batches,photo-manifest}.csv` (`EXPORT_ALL` permission): refuses anything not `status=APPROVED`, anything with no `approval_hash`/`company`/`rows` recorded, and (defense in depth) anything whose frozen payload no longer matches its recorded `approval_hash` -- all via `ErpNextExportFileService.generate_file()`, which builds CSV bytes as a pure function of the frozen `rows`/`company`/`session_id`/`export_id` only. Stock Entry uses `erpnext_opening_qty` (never variance/adjustment); Stock Reconciliation uses `counted_qty`/`existing_sql_qty`/`erpnext_adjustment_qty` (never variance); Serials emits one row per serial; Batches de-duplicates by `batch_no` (first occurrence wins for date fields); Photo Manifest emits `photo_proofs` references only (id/url/timestamp), never `photo_base64`, with `Photo Type`/`Captured By` left blank since no such data is captured anywhere (not fabricated). Each file's sha256 hash is stored on the preview on first generation only (idempotent: identical rows produce identical bytes/hash, so repeat downloads don't re-write metadata or re-audit); a hash mismatch on regeneration is treated as a critical integrity error, not silently served. Every first-time generation writes an `EXPORT_FILE_GENERATED` audit event. Verified: downloading never touches `count_lines`, never mutates the approved preview's `rows`/`approval_hash`/`status`. File generation additionally blocks if any correction proposal for this `export_id` is still `PENDING`.
- Correction proposal workflow (`erpnext_export_correction_proposals`): `POST /api/erpnext-exports/{export_id}/corrections` (supervisor, `EXPORT_ALL`) creates a `PENDING` proposal against a not-yet-approved preview row, restricted to a fixed allow-list (`erpnext_warehouse`, `batch_no`, `serial_numbers`, `photo_proofs`, `mrp`, `manufacturing_date`, `expiry_date`, `remarks`) -- any other field (quantities, hashes, identity fields) is rejected with 422; a missing `reason` is also 422; proposing against an `APPROVED` preview is rejected. `POST .../corrections/{proposal_id}/{approve,reject}` (admin-only) transition a `PENDING` proposal to `APPROVED`/`REJECTED` (both terminal, never re-reviewable); rejected proposals remain stored and auditable, never deleted. Nothing is ever written to the preview the proposal targets -- an `APPROVED` proposal instead gets picked up automatically the next time `generate_preview()` runs for the same (session, mode, company) scope: the proposed fields are applied onto the newly-built row (and any blocker that field specifically resolves, e.g. `BATCH_REQUIRED_MISSING` when `batch_no` is corrected, is cleared), `applied_to_export_id` is stamped on the proposal, and an `EXPORT_CORRECTION_APPLIED` audit event is written referencing the new preview version. Both preview approval and file generation refuse to proceed while any `PENDING` proposal exists for that `export_id`.

Since `PhotoProof` (id/url/timestamp) never carries its own bytes, every `photo_proofs` entry is honestly classified `EXTERNAL_REFERENCE_ONLY` (or `UNKNOWN` if its source count_line has since vanished); a count_line's separate, single `photo_base64` field, when present, is captured as its own additional entry with `storage_kind=mongo_inline`, `durability_status=DURABLE`, and a real sha256 `content_hash` -- nothing is ever fabricated as durable. The manifest's own `manifest_hash` (sha256 of the canonical photo list) is deterministic; re-snapshotting unchanged evidence returns the existing manifest instead of creating a duplicate version (idempotent), while genuinely new evidence creates a new `manifest_version`. `photo-manifest.csv` (from Step 4) is enriched (additively) with `Content Hash`/`Durability Status`/`Manifest Hash` columns once a manifest snapshot exists for that export. Verified: creating a manifest never mutates the approved preview's `rows`/`approval_hash`/`status`; missing source count_lines never crash manifest creation.
- XLSX file generation: `GET /api/erpnext-exports/{export_id}/download/{stock-entry,stock-reconciliation,serials,batches,photo-manifest}.xlsx` (`EXPORT_ALL`, same route/guards as the CSV downloads) generates each file from the exact same `build_rows()` output the CSV endpoint uses -- fieldnames/rows are computed once and shared, so CSV and XLSX are guaranteed equivalent in content, column order, and row count by construction, not by convention. Each XLSX is a single worksheet with a sanitized, length-limited, character-safe sheet name; every cell is written as literal data via openpyxl's model API (never through a formula-evaluating path), and any string value that could be interpreted as a spreadsheet formula (`=`, `+`, `-`, `@`, tab, or carriage-return prefix) is neutralized with a leading apostrophe -- applied to both CSV and XLSX output, since it's the same OWASP CSV/Excel-injection vulnerability class regardless of format. `file_hashes`/`file_generated_at`/`file_generated_by` are now keyed per file type *and* format (`"stock_entry:csv"` vs `"stock_entry:xlsx"` are tracked independently), so generating one format never conflicts with or overwrites the other's hash; each format's `EXPORT_FILE_GENERATED` audit is written once, on that format's first generation only. - ERPNext import-template validation: `GET /api/erpnext-exports/{export_id}/validate/{file_slug}` (`EXPORT_ALL`, all 10 CSV/XLSX slugs) is a read-only check (never talks to ERPNext, never requires credentials) that a given file type/format would satisfy ERPNext's import template. `ErpNextImportValidationService` maintains its own hardcoded `REQUIRED_COLUMNS` per file type -- deliberately not derived from the file generator's own fieldnames, so drift between "what we generate" and "what ERPNext's template requires" is actually detectable. It checks: preview exists and is `APPROVED`; `company` and `approval_hash` are present and the hash matches the frozen payload; no row carries a blocker (re-inspecting each row's own frozen `blockers` list as a safety net, since an `APPROVED` preview is guaranteed to have none today); per-blocker-code checks for unknown/unmapped items, missing serials on serialized items, missing batch numbers on batch-controlled items, and high-risk items missing evidence; warehouse/UOM mapping presence per row; required columns present and in stable order; required row values non-blank; the actually-rendered file bytes' header row matches the expected fieldnames (closing the loop on the real serialization layer); and, if the file has already been generated, that its stored `file_hash` still matches a fresh render (otherwise a `FILE_NOT_YET_GENERATED` warning, not an error). Returns `{valid, file_type, format, errors, warnings, row_count, column_count}`.
